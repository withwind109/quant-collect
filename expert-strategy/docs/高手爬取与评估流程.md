# 高手爬取与评估流程报告

> 版本：2026-10-19 v2 · 对应代码：expert-strategy（FastAPI + 原生 HTML）
> 当前架构：**仅东财实盘一条链路**（模拟盘通道、历史批量回补已于 2026-10-19 整体删除）。
> 本文说明数据怎么进来（爬取链）、高手怎么评出分（评估链），以及两者的衔接与自动化机制。

---

## 0. 一页全景

```
┌────────────────────────── 爬取链（仅实盘） ──────────────────────┐
│  ① 实盘高手榜（rtV1，无需登录）                                    │
│     页面「⬇ 加载最新」→ POST /live-experts/refresh（日榜→总榜）     │
│     → upsert crawl_expert（今日快照 + fetched_at 拉取时间）        │
│     → 页面加载时直接从本地渲染，刷新不丢                            │
│                                                                  │
│  ② 关注组合调仓明细（rtV3，仅对关注者开放）                         │
│     web/scheduler.py 守护线程：启动后 20s 首拉 + 每 8 小时一次      │
│     + 页面手动「拉取调仓明细」/「⟳ 更新」                          │
│     → fetch_live_trades() → crawl_trade(live)（row_sig 幂等去重） │
│     → 每次拉取写一行 xcq_fetch_log（新鲜度数据源）                  │
└────────────────────────────────────────────────────────────────┘
                              ↓ 滚动累积
┌──────────────────────────── 评估链 ─────────────────────────────┐
│  页面「▶ 开始评估」                                               │
│    → POST /api/expert-crawl/evaluation/run → expert_eval 子进程   │
│        ① load_expert_signals：live 流水 → normalize_live 仓位重建    │
│        ② _kline_for：补行情（东财→腾讯兜底）→ 本地 K 线索引         │
│        ③ simulate_expert：逐高手镜像回测（等同无脑跟单）            │
│        ④ compute_metrics：全套盈利指标                             │
│        ⑤ _assign_scores：分位秩综合评分 → 排序                     │
│        ⑥ 写 data/eval/latest.json（Web 页直接读）                  │
└────────────────────────────────────────────────────────────────┘
```

**衔接点**：榜单只提供收益快照（发现高手）；rtV3 只有关注组合才拿得到（评估样本）。
评估列表**默认只看关注的高手**，并展示每人的**数据新鲜度**（最近调仓日期 + 最近拉取时间），
过旧（>7 天未拉取）标红提醒手动更新。

## 1. 爬取链：数据怎么进来

### 1.1 两个入口

| 数据 | 触发方式 | 落库 |
|---|---|---|
| 实盘高手榜（rtV1 日榜 10005 + 总榜 10004） | 页面「⬇ 加载最新」手动触发（带进度条）；CLI `python main.py crawl` 仍可用 | `crawl_expert`（今日 upsert，带 `fetched_at`） |
| 关注组合调仓明细（rtV3 最近 40 条/组合） | **自动**：`web/scheduler.py` 启动 20s 后首拉 + 每 8h；**手动**：关注列表「拉取调仓明细」、评估表行内「⟳ 更新」 | `crawl_trade`(live)（row_sig 去重）+ `xcq_fetch_log` |

### 1.2 rtV3 自动拉取调度器（`web/scheduler.py`）

- 服务启动（`app.py` lifespan）拉起守护线程：延迟 20s 首拉（等建表/登录态就绪），之后每 8 小时一次。
- 拉取逻辑与手动入口共用 `routes/experts.py: fetch_live_trades()`（对全部 live 关注组合调
  rtV3 `CombinationRelocatePositionHandler`，pageSize=40 为服务端硬上限）。
- 未登录 / 关注列表为空 → 本轮跳过并记日志，扫码后下一轮自动生效。
- 每次拉取按 `row_sig`（日期+源+组合+股票+方向+时间+价+权重）幂等去重，**滚动累积**评估样本；
  同时写一行 `xcq_fetch_log`（即使 0 新增也记录"上次拉取时间"）。

### 1.3 rtV3 明细的深度与粒度（2026-10-19 实测）

| 维度 | 实际情况 |
|---|---|
| 时间深度 | 单次固定**最近 40 条**（翻页参数被服务端忽略，无法回溯更早）；关注后靠定时拉取滚动累积 |
| 单条字段 | 日期+**精确到秒**的时间、股票代码/名称/市场、买卖方向、成交价、数量、仓位档位（"1成"等中文粗粒度） |
| 局限 | 无完整持仓快照（只有调仓动作）；卖出分不清清仓/减仓；无买入金额 |

### 1.4 抓取后端（反爬设计）

- 榜单 rtV1：轻量 HTTP（`HttpClient`）。
- rtV3 固定走 curl HTTP 客户端（SM4 签名信封；无头浏览器后端发该 POST 会被服务端回 400）。
- 登录态：右上角「🏦 账户中心」扫码 → `broker_accounts` 存 ctToken/utToken/userId，
  心跳线程每 30min 续期。

### 1.5 组合可见性：为什么有些人「看不到 / 关注不上」

东财实盘链路把组合分成三种可见状态，只有第一种能拿到流水：

| 状态 | 平台返回 | 能否关注 | 能否取数 | 典型场景 |
|---|---|---|---|---|
| 公开 | 组合信息可查；rtV3 code=0 | ✅ `srtV1 result=0` | ✅ 最近 40 条 | 榜上的多数组合 |
| 私密（仅隐藏调仓） | 组合信息可查；rtV3 **30001**「用户暂未授权公开持仓/调仓记录」 | ✅ | ❌ | 赖哥最稳（900023658） |
| 隐藏/关闭关注 | 组合信息 **9062**「该组合已隐藏」；关注 **-10312**「组合加自选失败」；rtV3 30001 | ❌ | ❌ | 凡人炒股（900407488） |
| 不存在/已删除 | 组合信息 **9061** | ❌ | ❌ | 狐狸大王呀（900457430） |

要点：

- **不在榜 ≠ 不存在**。`rtV1` 各榜都只翻到约 400 行（`recIdx≥600` 起返回空），
  全站几千个组合里只有排行前几百可见；榜单也**没有**任何按昵称/组合号检索的接口
  （`rt_get_zh*` 等 type 一律 400，rtV3 只认 `CombinationRelocatePositionHandler`
  / `CombinationInfoHandler` / `FollowCombinationQueryHandler` 三个 method）。
  所以「APP 里能看到某人，页面①搜不到」是必然的——**入口只能靠组合号**。
- 因此 ② 关注列表提供**手动按组合号关注**（`GET /watchlist/probe` 先探测再
  `POST /watchlist`）。平台拒绝关注时本地仍保留该条（note 记 `东财拒绝：…`），
  一旦组合主放开隐私，下一轮定时拉取会自动恢复取数。
- 每轮 rtV3 探测结果落 `xcq_combo_status`（expert_id/code/message/n_rows/checked_at），
  页面「取数状态」列与评估表「数据新鲜度」列直接展示 `30001 / 9061 / 9062 / -1`，
  不再把"平台不给"显示成"未拉取"。
- ① 榜底部会列出**已关注但不在榜**的组合，避免误以为关注丢了。

## 2. 评估链：高手怎么评出分

### 2.1 信号来源与仓位重建（`load_expert_signals` / `normalize_live`）

- **仅 live**：`expert_trades` 视图（`crawl_trade` 的 `market_type='live'` 投影），传 `env='sim'` 直接 `ValueError`。
- **能被评估的必然是关注过的高手**：rtV3 明细仅对关注者开放，未关注组合只有榜单快照、没有流水。
- ⚠️ **rtV3 的 `positionRatio` 不是调仓后仓位**：它是「成交金额 / 组合总资产」按"成"向下取整的分档
  （`1成以下`→约 6%、`k成`→约 k×10+5%、`9成以上`→约 95%），且 `1成` 的卖出有 57% 是整只清仓。
  直接当目标仓位用会留下卖出后的"幽灵仓位"（源项目实测期末持仓 84% 是幽灵仓位，实盘回测全部作废）。
- 因此评估前必须先用 `strategy/pit_nav.normalize_live` 做「现金 + 持仓」记账重放：
  买入金额 = 档位中点 × 总资产（不超过现金）、**每笔卖出按清仓处理**，还原每条记录真实的
  `weight_before / weight_after`，再进入镜像回测。
- 重建体检（`health`，随评估结果透出）：
  - 无原文（weight_label 缺失）→ 零星记录丢弃并记缺口日，成段缺失只用之后连续区间；
  - 卖出"从未见过买入"→ 起点持仓按卖出比例回填（`seeded`），超过阈值判为"起点持仓不明"，整组不可用；
  - `phantom_end`（期末幽灵仓位数）应为 0；不可用组合进入 `meta.skipped` 并在页面提示原因。
- 港股/无行情代码（rtV3 里有 `market=5` 的港股，如 02362）会被价格面板剔除，不参与评估。
- 过滤条件：`stock_code` 非空 **且** 重建后 `weight_after` 非空。

### 2.2 行情与基准

- `_kline_for`：先查「无行情代码」跳过缓存（`data/eval/price_miss.json`，7 天过期）→ 缺的调
  `prices.ensure_prices` 补（akshare 东财主通道，失败切腾讯 gtimg 兜底）→ 本地 `prices.db` 建索引。
- 基准：`index_closes("000300.SH")` 沪深300。

### 2.3 镜像回测（`simulate_expert`，口径与跟随回测单一事实源）

把高手的调仓记录当作「无脑跟单」跑一遍，常量全部从 `follow_backtest.py` 导入（改一处两边跟随）：

| 环节 | 规则 |
|---|---|
| 信号→目标 | 同一高手同一股票同一交易日，取**日终净目标权重**（重建后的 weight_after 最后一条，后到者覆盖；每笔卖出按清仓=0） |
| 执行 | **T+1 开盘价**成交，滑点 ±0.2%；整百股 |
| 费用 | 佣金万 8（最低 5 元）；**卖出加收印花税万 5** |
| 约束 | 开盘涨停拦截（记 `buy_skipped`）；目标权重 <1% 视为清仓/噪音；变动 < max(500 元, 净值 0.2%) 不调仓；现金不足时按可买量下调 |
| 窗口 | 从该高手**首笔信号日**起（之前没单可跟，净值持平无意义） |
| 停牌/缺行情 | 顺延不了就放弃（与原引擎一致） |

> 口径对齐源项目 xcq-platform `live3_mirror`（exec: t1_open 镜像持仓）。

### 2.4 指标（`compute_metrics`）

- **收益类**：总收益率、年化（365 天折算）
- **风险类**：最大回撤、Calmar（年化/回撤）
- **风险调整**：夏普（√252）、索提诺（只用下行偏差）
- **交易类**：胜率、平均盈利/亏损、盈亏比（按卖出笔统计）
- **相对基准**：超额收益（同时段沪深300）、Alpha·Beta（日收益对中证500 回归，含 t 值）

### 2.5 综合评分与样本门槛

- **评分** = 夏普、索提诺、Calmar、胜率四项的**分位秩平均 ×100**（0-100）。
- **样本门槛**：卖出 < 3 笔 或 覆盖 < 20 个交易日 → `sample_ok=False`，不给分、排序沉底——避免用 3 笔交易谈夏普。
- 排序：样本充足者优先 → 评分降序 → 夏普降序，赋 rank。

### 2.6 评估页视图（2026-10-19 新增）

- **默认只看关注**（「只看关注」勾选，默认开）：列表只显示关注列表（live）里的高手；
  取消勾选可看全部有流水的高手。
- **数据新鲜度列**：每行展示「最近调仓日期（N 天前）+ 最近拉取时间（M 小时前）」，
  从 `GET /watchlist/freshness` 实时读取（不依赖评估快照）；**>7 天未拉取标红「过旧」**，
  从未拉取标「未拉取」，**平台拒绝取数的直接标「⛔ 取数受阻 + code」**（优先于"未拉取"）。
- **行内「⟳ 更新」按钮**：对关注高手单独立即重拉 rtV3 并入库，完成后新鲜度自动刷新。
  更新后需重新「开始评估」才能反映到指标（评估结果是静态快照）。

## 3. 数据持久化与新鲜度（2026-10-19 新增）

| 机制 | 说明 |
|---|---|
| 榜单持久化 | `crawl_expert` upsert 今日快照，`fetched_at` 列记录拉取时间；页面加载即从本地渲染（刷新不丢），meta 显示「数据日期 X · 榜单拉取于 Y」 |
| 调仓流水累积 | rtV3 定时 + 手动拉取滚动累积；`crawl_trade.fetched_at` 记录每条流水首次入库时间 |
| 拉取日志 | `xcq_fetch_log`（id/expert_id/fetched_at/n_total/n_new/trigger）——0 新增也记录，是新鲜度判断的依据 |
| 新鲜度规则 | `stale` = 从未拉取 或 最近拉取距今 >7 天（评估样本可能已断更） |
| 样本积累期 | rtV3 单次只有 40 条，一次性回补不可行；对齐源项目 `min_days: 60` 的口径，评估结论需要几周积累期 |

## 5. 审计修复记录（2026-10-19 v3 · 数据正确性专项）

| # | 问题 | 影响 | 修复 |
|---|---|---|---|
| 1 | rtV3 `positionRatio` 被当成「调仓后仓位」 | 卖出后留幽灵仓位；实测 40 条流水只出 13 买 0 卖、总收益 -11%、夏普 -7.7 全不可信 | 评估改走 `pit_nav.normalize_live` 记账重放（买=档位中点×总资产、卖=清仓），修复后 9 买 7 卖、总收益 -3.94%、回撤 3.94% |

## 7. 评估口径 vs 东财 APP 数字（2026-10-19 财神咒案例）

**现象**：财神咒（900242532）APP 显示总收益 3293.57%、近一月 23.12%、近1年 145.10%、
本月最大回撤 3.73%、日收益 -1.29%；本系统评估 -1.57%、回撤 2.95%。用户质疑算错。

**归因（scripts/_diag_csz.py 实测）**：

| 层 | 数字 | 说明 |
|---|---|---|
| K 线质量 | 40/40 通过 | rtV3 真实成交价全部落在当日 open~close ±3%，新浪北交所数据无误 |
| 专家自身口径重放（真实成交价、0 延迟） | **+5.49%** · 回撤 1.25% | 9/23~10/19，40 条流水内他自己的账 |
